# AM-DMF 双层框架的 C++ 复现

本工程依据论文 [A Two-Layer Decoupled Synthesis Framework for Uncertain Biochemical Protocols on Active-Matrix Digital Microfluidic Platforms](https://doi.org/10.1109/TCAD.2026.3721419) 逐步复现。论文给出了框架和伪代码，没有公开完整实现与实验生成程序。工程使用 C++17，文档使用中文。

当前 `main` 分支处于 **v0.8：异步代价场更新**。每个正式版本都用 Git 标签保存；桌面的 `PROJECT/versions/版本号` 是可独立用 Visual Studio 打开的源码副本。此前可运行但简化较多的探索原型保存在 Git 标签 `v0.0-prototype`，不作为论文数值复现结果。

## 先理解两个图

- **CFG**：协议可能走的流程。例如检测通过后输出，失败后丢弃。两条路都预先写在 CFG 中，但运行时只会选择实际发生的一条。
- **block DAG**：一个流程块内部的操作与输入关系。例如混合产生液滴，检测必须等这滴液体产生后才能开始。
- **dynamic DAG**：运行中已激活流程块的操作集合。检测结果到来时，才把选中的后续流程块加入其中。同一个流程块因重试而执行两次，会产生两套不同的运行实例。

## v0.1 已实现

| 部分 | 职责 |
| --- | --- |
| `include/dmf/protocol.hpp`、`src/protocol.cpp` | 定义 CFG、流程块、操作和液滴输入引用；检查块内 DAG 是否有环、分支目标和输入引用是否有效。 |
| `include/dmf/dynamic_dag.hpp`、`src/dynamic_dag.cpp` | 记录已激活的流程块、每次执行的操作编号、液滴是否可用，并根据检测结果在下一周期激活分支。 |
| `src/main.cpp` | 用“混合 → 检测 → 输出或丢弃”的小例子打印流程。完成事件由示例程序手动提供。 |
| `tests/runtime_tests.cpp` | 检查依赖、分支选择、重试产生新实例、液滴不可重复使用，以及错误反馈不改变运行状态。 |

v0.1 用两个条件判断操作是否**就绪**：生成输入液滴的操作已经完成，而且所需液滴当前可用。从 v0.2 开始，选址时会预留输入液滴，到达后才启动操作。完成操作产生的新液滴到下一周期才可供后续操作使用；检测结果也在下一周期激活选中的流程块。

## v0.2 新增：从就绪到真正启动

v0.2 把“输入已具备”和“操作开始执行”拆成四步：

```text
输入可用 → 操作就绪 → 选址并预留输入液滴、虚拟模块
         → 发出液滴运送请求 → 所有输入液滴到达 → 启动并形成运行障碍区
         → 收到完成反馈 → 释放模块、登记输出液滴的位置
```

| 代码 | 职责 |
| --- | --- |
| `dynamic_dag.hpp/.cpp` | 新增 `Placed` 状态；选址时预留液滴，避免别的操作重复使用；到达后才进入 `Running`。 |
| `placement.hpp/.cpp` | 建立虚拟模块网格，选择离输入液滴平均位置最近的空闲模块，并记录模块预留。 |
| `upper_layer.hpp/.cpp` | 串起就绪操作、选址、运送请求、到达反馈、启动、完成和释放。`RoutingTask` 是上下层交换的数据接口。 |
| `tests/placement_tests.cpp` | 检查最近选址、模块和液滴不能重复预留、等待所有液滴、完成后释放，以及错误反馈不会提前释放模块。 |

本版先支持 **Mix（两个输入）** 和 **Detect（一个输入）** 的虚拟模块选址。`Output`、`Waste` 等操作仍可在 v0.1 的纯逻辑示例中运行，但还没有物理端口模型。

### 论文规则与工程假设

论文上层根据就绪操作的输入液滴位置，在虚拟拓扑中寻找未占用模块；操作启动后，将其位置作为下层需要避开的 blockage。本工程为可运行示例补充以下具体规则，**这些数字与选点方法不是论文公开的固定参数**：

- 一个虚拟模块占 `3×3` 个电极；模块之间留一整块模块宽度的通道。第一个模块左上角坐标为 `(3,3)`。
- 用输入液滴坐标的平均位置衡量距离；若距离相同，按从上到下、从左到右的顺序选模块。
- Mix 的两滴输入分别以模块中心左、右相邻电极为目标；Detect 的目标是模块中心。输出液滴的位置暂记在模块中心。
- 选址时就预留模块和输入液滴；只有操作真正启动时，该模块才出现在 `activeBlockages()` 中。
- 在 v0.2 中，液滴“已到达”和操作“已完成”由示例或测试手动报告；实际移动在 v0.3 接入。

v0.2 只能验证上层状态衔接和选址规则，不能作为论文路由效果的对照结果。

## v0.3 新增：按反馈逐步移动

v0.3 在 `RoutingTask` 对应的目标与 `UpperLayer` 之间接入 `Router`。整个演示的数据流是：

```text
就绪操作 → 上层选址 → RoutingTask → Router 规划下一步
                                  ↓
                         实际位置反馈、检查是否到达
                                  ↓
                      上层确认全部到达且操作区空闲 → 启动
                                  ↓
                      操作区域成为 blockage → Router 更新
```

| 代码 | 职责 |
| --- | --- |
| `routing_task.hpp` | 上下层共同认识的液滴编号、目标电极和操作编号。 |
| `router.hpp/.cpp` | 保存待运送任务；为每个目标用 BFS 生成代价场；每一步结合最新障碍和液滴位置选择动作；根据实际位置反馈判断到达。 |
| `upper_layer.hpp/.cpp` | 与 Router 共用同一份液滴位置；到达反馈必须与真实目标坐标一致，且模块内没有其他液滴才启动操作。 |
| `tests/router_tests.cpp` | 验证单滴移动、移动失败、动态障碍、多滴迎面相遇与代价场缓存。 |

### 路由规则与实时性

- 每个控制步只考虑上下左右四个相邻电极；没有安全动作时原地等待。Router **规划**动作后再接收**实际位置反馈**。若电极动作失败，位置保持原样，下一步依实际位置重新决策。
- 在当前障碍布局下，每个目标执行一次 BFS；同一目标可复用。操作障碍区改变时才清除旧场，下次使用时重建。普通控制步无需重算整张芯片的场。完成的目标若不再有任务使用，缓存会释放。
- 安全距离暂设为两滴液体的 Chebyshev 距离至少为 2，即水平、竖直和斜方向相邻都不允许。规划下一步时检查其他液滴的当前位置、上一时刻位置以及本步已规划位置。这是可配置的**工程假设**，不是论文公开的固定数值。
- 迎面相遇时用两步前瞻比较候选动作，并在平局时让不同编号的液滴偏向不同侧绕行；立刻退回上一个电极会增加 3 的选择代价。这两个确定性选择是为了复现可检查的绕行行为，**不是论文给出的固定参数**。
- v0.3 的 BFS 更新是按需同步执行；v0.8 对已缓存目标在环境变化后的重算加入后台线程。新目标的第一次代价场仍同步生成，保证当步有路线可用。当前示例只模拟电极位置和反馈，不生成真实驱动信号。

`Router` 的状态与操作完成仍分开：液滴真实到达会自动通知上层；Mix、Detect 的完成时刻和输出编号在示例中仍由程序报告。`cycle` 目前只是 dynamic DAG 的逻辑周期，不等于论文的物理执行周期。

## v0.3.1 新增：自己设置起点和终点

这一版增加了独立的 `dmf_custom_route.exe`。它只使用下层 Router，不运行 `Mix → Detect` 协议或上层选址。你可以在 `examples/route_case.txt` 中填写阵列尺寸和多滴液体的起终点；重新运行程序就会读取新内容，无需重新编译。默认文件如下：

```text
chip 5 5
separation 2
max_steps 50
trace 1
droplet 1 0 0 4 4
```

`chip` 后是阵列宽度、高度，所以这里是 `5×5`；坐标从 `(0,0)` 开始。`droplet` 一行依次写“编号、起点 x、起点 y、终点 x、终点 y”。增加更多 `droplet` 行即可测试多滴液体。`separation` 是可配置的安全距离；`max_steps` 是最多尝试的控制步数；`trace 1` 打印每一步，`trace 0` 只显示到达事件与最终结果，可减少大量控制台输出。以 `#` 开头的文字是注释。

输入会检查阵列大小、坐标范围、重复编号和起点安全距离。当前实验入口限制为最多 90000 个电极、400 滴液体、100000 个控制步，以免误填参数后长时间占用计算资源。若超过步数，程序会列出尚未到达的液滴、当前位置和目标位置；连续 10 步没有任何液滴移动时也会停止。**停止只说明当前路由策略未完成这次实验，不证明该布局在数学上无解。**

输入文件在程序启动时解析一次；正常控制步仍使用 v0.3 的 Router 与代价场缓存。打印大量轨迹会影响你观察到的总运行时间，因此需要评估计算性能时应将 `trace` 设为 `0`。目前没有把这项自定义实验的运行时间当作论文性能复现结果。

## v0.4 新增：操作计时与逐步协同

以前的双层演示需要手动报告 Mix、Detect 何时完成。现在 `ExecutionLoop` 把上层、Router 和操作完成反馈接到同一个**模拟控制步**中。`ModuleProfile` 增加 `duration_cycles`；演示用 Detect 的时长为 3 个运行控制步。这个数值是为了验证事件顺序而设的工程假设，论文中的具体操作时长应在复现实验参数确定后另行填写。

每一步按以下顺序执行：

```text
上一步的输出液滴和分支变为可用
    → 上层为就绪操作选址、预留液滴与模块
    → Router 接收任务；已在目标的液滴可立即触发操作启动
    → Router 读取当前运行模块的 blockage
    → Router 规划一步、收到模拟的实际位置反馈
    → 全部输入到达且模块空闲时，操作开始运行
    → 只给进入本步前已经运行的操作计时
    → 到时收到完成反馈、释放模块；输出下一步才可用
```

例如时长为 3 的操作若在第 1 步启动，第 2、3、4 步末分别消耗一个运行步，在第 4 步末完成。同一时间，其他液滴仍可继续路由。操作一开始，模块区域成为 blockage；完成时立即解除。`completeEarly` 可提前提交实际完成反馈并释放模块，输出仍从下一步开始可用。到达晚于预计时间的操作不会提前计时，模块也只有在真正启动后才成为运行障碍。

v0.4 的 `timed` 演示放置两项独立 Detect：近处液滴立即启动，另一滴在操作运行时继续前进。每步会显示移动、启动、完成及 blockage 数量；结束时显示代价场构建次数和 Router 决策的累计微秒数。计时只包住 `Router::planStep()`，不含控制台打印、上层选址、模拟反馈，也不代表硬件实时性保证。控制循环在单线程中按序模拟“路由与操作在同一时间段推进”，尚未实现后台计算线程或真实电极驱动。

`tests/execution_tests.cpp` 检验并行推进、操作时长、动态 blockage、输出下一步可用与提前完成；此前的测试仍保留。

## v0.5 新增：实际位置反馈与强制绕障

v0.4 的控制循环总假设液滴按命令成功移动。现在可向 `ExecutionLoop` 提供一个移动反馈函数：每收到一条移动命令，返回这一控制步观测到的液滴位置。反馈可为原位置（移动失败）或命令指定的下一位置（移动成功）；Router 会检查反馈是否合法，并以**实际位置**判断是否到达、下一步从哪里继续规划。`StepReport` 同时保留 `moves`（计划动作）和 `observed`（实际反馈）。不提供反馈函数时，沿用原先“移动总成功”的默认行为。

默认 `detour` 演示仍使用 **15×9** 阵列，两滴液体的起点改为 `(4,4)` 和 `(0,4)`；液滴 2 的目标是 `(10,4)`。横向直走会穿过 near 操作占用的 `x=3～5、y=3～5`，因此它必须先离开 `y=4`，绕过活动模块。示例把两项 Detect 的运行时长都设为 20 个控制步，并在第 2 步故意让液滴 2 的一次移动失败；这些数值和失败事件都是**用于验证的工程设置**，不是论文实验参数。

控制台的 `planned=(x,y)` 是 Router 希望到达的位置，`actual=(x,y)` 是反馈确认的位置。第 2 步会出现 `FAILED`，第 3 步重新从实际位置出发；液滴 2 随后沿上方绕行，并在 near 尚未完成时启动 far，此时 `blockages=2`。完成反馈和先前版本一样使模块释放。测试另外覆盖“最后一步移动失败时不能误报到达和启动操作”，并检查绕行期间不进入活动模块、最终完成两项操作。

此反馈入口用于模拟电极位置观测，尚未连接真实传感器。微秒计时仍仅统计 Router 规划动作，不含反馈函数和控制台输出。

## v0.6 新增：一条协议从输入跑到输出或废液口

之前动态 DAG 的分支演示和双层控制循环分别运行。这一版让同一条协议在一个控制循环里完成：

```text
输入液滴 1、2 → Mix → 新液滴 3 → Detect → 新液滴 4
                                           ├─ 检测结果为 output → 送到输出口
                                           └─ 检测结果为 waste  → 送到废液口
```

上层仍为 Mix、Detect 选择虚拟模块，等输入液滴到齐后启动并形成 blockage。对于 Output、Waste，上层读取预设的阵列边缘端口，生成普通 `RoutingTask`；Router 使用同一套逐步移动与到达反馈。端口不占用虚拟模块，也不形成操作区域障碍。到达端口后，终点操作在下一控制步完成并消耗该液滴。检测结果由仿真反馈提供，选中的流程块在检测完成后的下一步才加入动态 DAG；另一条分支不执行。

v0.6 示例使用 **15×9** 阵列，初始液滴分别位于 `(1,2)`、`(1,6)`，输出口为 `(14,4)`，废液口为 `(0,8)`。Mix 用时 3 个运行控制步，Detect 用时 2 个运行控制步，终点操作用时 1 个运行控制步。这些位置和时长是演示事件衔接的**工程假设**，并非论文实验参数。运行 `am_dmf protocol` 会连续展示 output 和 waste 两次独立仿真；每行显示本步新激活的分支、运送目标、液滴移动、操作启动与完成、活动 blockage 数量。示例结果分别在第 23 步和第 21 步结束，最终活动液滴数均为 0。具体完成步数依本工程的路由规则和演示参数而定，不是论文实验结果。

`tests/protocol_execution_tests.cpp` 检查两条分支、操作依赖和分支时序、端口到达后才能启动、终点消耗液滴、安全距离，以及无效或缺失端口。此前版本的演示和测试保留。

在 Visual Studio 里通过“文件 → 打开 → 文件夹”打开 `PROJECT/versions/v0.6`，在绿色运行按钮旁选择 **`am_dmf.exe`**，按 **Ctrl+F5** 即可看到两条分支的完整过程；无需打开“调试和启动设置”。在当前版本中，可使用 PowerShell 命令 `am_dmf.exe protocol` 运行相同演示。想只看一条分支，可运行 `am_dmf.exe protocol-output` 或 `am_dmf.exe protocol-waste`。选择 **`dmf_protocol_execution_tests.exe`** 并按 Ctrl+F5，会看到 `protocol execution tests: passed`。

## v0.7 新增：新操作区域启用前撤离无关液滴

上层为操作选定虚拟模块后，先把它标记为**即将占用的区域**，并把该区域和本操作的输入液滴编号通知 Router。Router 允许本操作的输入液滴进入，同时引导其他液滴避开该区域。如果无关液滴已经在里面，Router 用 BFS 搜索最近且可安全到达的区域外电极，临时将其作为撤离目标。液滴离开后，原来有运送任务的继续去原目标；原本没有任务的停在安全位置。只有输入液滴到齐、区域内没有无关液滴时，上层才启动操作并把区域变为正式 blockage。

```text
选址并预告区域 → 发现区域内的无关液滴 → 撤离到安全出口
            → 输入到齐且区域清空 → 启动操作 → 正式形成 blockage
```

默认 `evacuation` 演示使用 **9×9** 阵列：Detect 的输入液滴 1 起于 `(4,3)`，无关液滴 99 起于预留模块内的 `(4,5)`，模块范围是 `x=3～5、y=3～5`。第 1 步液滴 99 移动到 `(4,6)`；输入液滴继续前进，第 5 步才到位并启动 Detect，第 7 步完成。控制台会显示撤离目标、移动、清空区域、操作启动与完成，以及 blockage 数量。液滴 99 不属于该操作，检测完成后仍留在安全位置。

`tests/evacuation_tests.cpp` 检查静止液滴撤离、有原任务的液滴撤离后恢复、撤离移动失败后按实际位置重试、无安全出口时保持等待，以及区域正式启用前其他液滴不进入。`StepReport` 的 `evacuation_targets`、`evacuated` 和 `waiting_for_evacuation` 用于解释每一步发生了什么。

**当前工程规则：**即将占用的区域对无关液滴立即视为禁入，撤离出口按最短可行步数选取；相同步数按固定邻居顺序决定。论文提到按预计占用时间提前预告，并允许液滴在启用前视情况穿过区域。本版采用较保守的禁入规则，尚未建立精确的未来占用时间窗口。移动失败仍由 v0.5 的实际位置反馈处理；若没有安全出口，系统报告等待，不强行启用障碍。新障碍未经预告、直接困住液滴的处理仍待后续实现。这里的演示位置和时长是工程假设，不是论文实验数据。

## v0.8 新增：操作区域变化时异步更新代价场

代价场记录每个电极到目标的最短剩余步数。v0.7 在障碍变化后的首次路由决策中同步重算整张场；v0.8 把**已有目标的重算**交给一个后台工作线程。Router 先拍下障碍和预告区域的不可变快照，再发出更新任务。后台完成前，旧代价场只用于判断哪个方向更有希望；每个候选位置仍必须通过**当前**障碍、预告区域和液滴安全距离检查。新场准备好后，Router 在控制步边界切换。连续变化时只保留每个目标最新版本，旧计算结果不会覆盖新结果。

```text
障碍变化 → 保存当前布局快照 → 后台计算新版代价场
                 ↓                       ↓
      当前障碍继续做安全检查       完成后按版本号安装
                 ↓                       ↓
            旧场暂时指导方向 → 下一控制步使用新场
```

默认 `am_dmf.exe` 演示使用 **120×120** 阵列，液滴从 `(0,60)` 运送到 `(119,60)`。第 10 步在 `x=55～65、y=55～65` 加入障碍，第 40 步移除。控制台会显示变化通知、旧场使用、新场启用、最终到达、总步数和等待步数。后台计算结束的具体步数受系统线程调度影响；运行时可能与示例截图不同。`am_dmf.exe evacuation` 保留 v0.7 的撤离演示。

工程中的异步边界是**障碍变化后的重算**：首次遇到一个全新目标仍同步构建代价场；显式测试等待函数用于测试，不在正常控制循环中调用。若旧场把可行方向估成不可达，液滴可能暂等新场，故本版保证的是每步安全性，不声称所有可达任务必然完成。`cost fields built` 只计入已安装的场，不包括被丢弃的后台旧版本。

`dmf_async_cost_field_tests.exe` 检查连续变化只接受最新版、旧场期间不进入新障碍、多个液滴共用目标，以及后台计算完成后的切换。`dmf_field_benchmark.exe` 对同一场景重复 10 次，分别统计“变化通知”和“变化后首次决策”的耗时中位数、总步数与等待步数；比较 v0.7 时需分别编译两个版本的 Release 程序。这个小场景只能检验局部开销与功能，不能替代论文的大规模实验或实时性上界证明。

## 当前边界与后续步骤

v0.6 已将 Mix、Detect、Output、Waste 贯穿到同一次仿真；v0.7 新增对**提前预告的操作区域**进行安全撤离；v0.8 对已有目标在障碍变化后的代价场重算使用单个后台线程。固定端口的位置、操作时长和撤离出口选择是工程假设。**还没有** Dispense、Split 的物理规则、未预告障碍困住液滴时的处理，也没有论文实验所用的大规模基准和对照结果。当前实现不生成真实电极驱动序列。

论文没有精确规定所有周期内事件的先后边界。当前固定为“本步完成的操作，其输出液滴和检测分支从下一步开始可用”；这是工程假设。`ExecutionLoop` 默认使用理想移动反馈，v0.5 允许注入失败或成功的位置反馈，但尚未接硬件反馈入口。

下一步计划按论文补充其余操作类型和实验基准，再决定未预告障碍的处理规则；PIBT 改进在原论文版本稳定后单独开展。每个完成版本都同时保存 GitHub 标签和 `PROJECT/versions/版本号` 的源码副本。
