# AM-DMF 双层框架的 C++ 复现

本工程依据论文 [A Two-Layer Decoupled Synthesis Framework for Uncertain Biochemical Protocols on Active-Matrix Digital Microfluidic Platforms](https://doi.org/10.1109/TCAD.2026.3721419) 逐步复现。论文给出了框架和伪代码，没有公开完整实现与实验生成程序。工程使用 C++17，文档使用中文。

当前 `main` 分支处于 **v0.2：上层选址与启动流程**。每个正式版本都用同名 Git 标签保存。桌面的 `PROJECT/versions/v0.2` 是可独立用 Visual Studio 打开的源码副本。此前可运行但简化较多的探索原型保存在 Git 标签 `v0.0-prototype`，不作为论文数值复现结果。

## 先理解两个图

- **CFG**：协议可能走的流程。例如检测通过后输出，失败后丢弃。两条路都预先写在 CFG 中，但运行时只会选择实际发生的一条。
- **block DAG**：一个流程块内部的操作与输入关系。例如混合产生液滴，检测必须等这滴液体产生后才能开始。
- **dynamic DAG**：运行中已激活流程块的操作集合。检测结果到来时，才把选中的后续流程块加入其中。同一个流程块因重试而执行两次，会产生两套不同的运行实例。

## v0.1 已实现

| 部分 | 职责 |
| --- | --- |
| `include/dmf/protocol.hpp`、`src/protocol.cpp` | 定义 CFG、流程块、操作和液滴输入引用；检查块内 DAG 是否有环、分支目标和输入引用是否有效。 |
| `include/dmf/dynamic_dag.hpp`、`src/dynamic_dag.cpp` | 记录已激活的流程块、每次执行的操作编号、液滴是否可用，并根据检测结果在下一周期激活分支。 |
| `src/main.cpp` | 用“混合 → 检测 → 输出或丢弃”的小例子打印流程。完成事件由示例程序手动提供。 |
| `tests/runtime_tests.cpp` | 检查依赖、分支选择、重试产生新实例、液滴不可重复使用，以及错误反馈不改变运行状态。 |

v0.1 用两个条件判断操作是否**就绪**：生成输入液滴的操作已经完成，而且所需液滴当前可用。在当前 v0.2 中，选址时会预留输入液滴，到达后才启动操作。完成操作产生的新液滴到下一周期才可供后续操作使用；检测结果也在下一周期激活选中的流程块。

## v0.2 新增：从就绪到真正启动

现在把“输入已具备”和“操作开始执行”拆成四步：

```text
输入可用 → 操作就绪 → 选址并预留输入液滴、虚拟模块
         → 发出液滴运送请求 → 所有输入液滴到达 → 启动并形成运行障碍区
         → 收到完成反馈 → 释放模块、登记输出液滴的位置
```

| 代码 | 职责 |
| --- | --- |
| `dynamic_dag.hpp/.cpp` | 新增 `Placed` 状态；选址时预留液滴，避免别的操作重复使用；到达后才进入 `Running`。 |
| `placement.hpp/.cpp` | 建立虚拟模块网格，选择离输入液滴平均位置最近的空闲模块，并记录模块预留。 |
| `upper_layer.hpp/.cpp` | 串起就绪操作、选址、运送请求、到达反馈、启动、完成和释放。`RoutingTask` 是以后接 Router 的数据接口。 |
| `tests/placement_tests.cpp` | 检查最近选址、模块和液滴不能重复预留、等待所有液滴、完成后释放，以及错误反馈不会提前释放模块。 |

本版先支持 **Mix（两个输入）** 和 **Detect（一个输入）** 的虚拟模块选址。`Output`、`Waste` 等操作仍可在 v0.1 的纯逻辑示例中运行，但还没有物理端口模型。

### 论文规则与工程假设

论文上层根据就绪操作的输入液滴位置，在虚拟拓扑中寻找未占用模块；操作启动后，将其位置作为下层需要避开的 blockage。本工程为可运行示例补充以下具体规则，**这些数字与选点方法不是论文公开的固定参数**：

- 一个虚拟模块占 `3×3` 个电极；模块之间留一整块模块宽度的通道。第一个模块左上角坐标为 `(3,3)`。
- 用输入液滴坐标的平均位置衡量距离；若距离相同，按从上到下、从左到右的顺序选模块。
- Mix 的两滴输入分别以模块中心左、右相邻电极为目标；Detect 的目标是模块中心。输出液滴的位置暂记在模块中心。
- 选址时就预留模块和输入液滴；只有操作真正启动时，该模块才出现在 `activeBlockages()` 中。
- 液滴“已到达”和操作“已完成”由示例或测试手动报告。操作时长、电极驱动序列、移动路线以及移动过程中的安全距离均尚未模拟。

因此，当前结果只能验证上层状态衔接和选址规则，**不能**与论文的执行周期数或路由成功率直接比较。

演示输出中的 `cycle` 目前只是这些事件的顺序编号。操作时长和真实芯片控制周期尚未接入，因此不能把它当作论文中的执行周期数。

## 编译与运行

需要 C++17 编译器和 CMake。在已配置好编译器的终端中执行：

```powershell
cmake -S . -B build
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

演示程序不填参数时直接运行 v0.2 的选址和到达反馈；也可显式传入 `placement`。`output` 和 `waste` 继续展示 v0.1 的 CFG 分支。使用 Visual Studio 多配置生成器时，例如：

```powershell
.\build\Debug\am_dmf.exe
.\build\Debug\am_dmf.exe placement
.\build\Debug\am_dmf.exe output
.\build\Debug\am_dmf.exe waste
```

若使用单配置生成器，可执行文件通常位于构建目录下。当前终端如果找不到 `cmake`，可在 Visual Studio 中通过“文件 → 打开 → 文件夹”打开 `PROJECT/versions/v0.2`，等待 CMake 配置完成后选择 `am_dmf.exe` 作为启动项，直接按 F5 即可运行 v0.2 示例。版本文件夹包含完整源码和 `CMakeLists.txt`，不依赖主工程的构建结果。若使用你之前那个设置了 `waste` 参数的启动配置，新文件夹里需选用它自己的启动项，才能运行默认的 v0.2 示例。

## 当前边界与后续步骤

v0.2 已有虚拟模块位置、选址、运行障碍区和向 Router 发出的任务数据。**还没有**真实液滴移动、动态路由、完整操作时长和电极驱动序列，也没有执行周期统计。示例中的到达、操作完成与检测结果由程序手动注入。

论文没有精确规定所有周期内事件的先后边界。当前固定为“本周期完成的操作，其输出液滴和检测分支从下一周期开始可用”；这是工程假设，后续实验会记录它对结果的影响。

下一步将围绕下层 Router 和上下层运行时反馈继续复现。完成论文原路由及双层联动后，再构造基准和对照方法；PIBT 改进在原论文版本稳定后单独开展。后续每个完成版本都同时保存 GitHub 标签和 `PROJECT/versions/版本号` 的源码副本。
