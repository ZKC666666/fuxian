# AM-DMF 双层框架的 C++ 复现

本工程依据论文 [A Two-Layer Decoupled Synthesis Framework for Uncertain Biochemical Protocols on Active-Matrix Digital Microfluidic Platforms](https://doi.org/10.1109/TCAD.2026.3721419) 逐步复现。论文给出了框架和伪代码，没有公开完整实现与实验生成程序。工程使用 C++17，文档使用中文。

当前 `main` 分支处于 **v1.9：对照出口位置和操作时长对第一类协议的影响**。每个正式版本都用 Git 标签保存，桌面的 `PROJECT/versions/版本号` 是可独立用 Visual Studio 打开的源码副本。此前的探索原型保存在 Git 标签 `v0.0-prototype`。

## 先理解两个图

- **CFG**：协议可能走的流程。例如检测通过后输出，失败后丢弃。两条路都预先写在 CFG 中，但运行时只会选择实际发生的一条。
- **block DAG**：一个流程块内部的操作与输入关系。例如混合产生液滴，检测必须等这滴液体产生后才能开始。
- **dynamic DAG**：运行中已激活流程块的操作集合。检测结果到来时，才把选中的后续流程块加入其中。同一个流程块因重试而执行两次，会产生两套不同的运行实例。

## v0.1 已实现

| 部分 | 职责 |
| --- | --- |
| `include/dmf/protocol.hpp`、`src/protocol.cpp` | 定义 CFG、流程块、操作和液滴输入引用；检查块内 DAG 是否有环、分支目标和输入引用是否有效。 |
| `include/dmf/dynamic_dag.hpp`、`src/dynamic_dag.cpp` | 记录已激活的流程块、每次执行的操作编号、液滴是否可用，并根据检测结果在下一周期激活分支。 |
| `src/main.cpp` | 用“混合 → 检测 → 输出或丢弃”的小例子打印流程。完成事件由示例程序手动提供。 |
| `tests/runtime_tests.cpp` | 检查依赖、分支选择、重试产生新实例、液滴不可重复使用，以及错误反馈不改变运行状态。 |

v0.1 用两个条件判断操作是否**就绪**：生成输入液滴的操作已经完成，而且所需液滴当前可用。从 v0.2 开始，选址时会预留输入液滴，到达后才启动操作。完成操作产生的新液滴到下一周期才可供后续操作使用；检测结果也在下一周期激活选中的流程块。

## v0.2 新增：从就绪到真正启动

v0.2 把“输入已具备”和“操作开始执行”拆成四步：

```text
输入可用 → 操作就绪 → 选址并预留输入液滴、虚拟模块
         → 发出液滴运送请求 → 所有输入液滴到达 → 启动并形成运行障碍区
         → 收到完成反馈 → 释放模块、登记输出液滴的位置
```

| 代码 | 职责 |
| --- | --- |
| `dynamic_dag.hpp/.cpp` | 新增 `Placed` 状态；选址时预留液滴，避免别的操作重复使用；到达后才进入 `Running`。 |
| `placement.hpp/.cpp` | 建立虚拟模块网格，选择离输入液滴平均位置最近的空闲模块，并记录模块预留。 |
| `upper_layer.hpp/.cpp` | 串起就绪操作、选址、运送请求、到达反馈、启动、完成和释放。`RoutingTask` 是上下层交换的数据接口。 |
| `tests/placement_tests.cpp` | 检查最近选址、模块和液滴不能重复预留、等待所有液滴、完成后释放，以及错误反馈不会提前释放模块。 |

本版先支持 **Mix（两个输入）** 和 **Detect（一个输入）** 的虚拟模块选址。`Output`、`Waste` 等操作仍可在 v0.1 的纯逻辑示例中运行，但还没有物理端口模型。

### 论文规则与工程假设

论文上层根据就绪操作的输入液滴位置，在虚拟拓扑中寻找未占用模块；操作启动后，将其位置作为下层需要避开的 blockage。本工程为可运行示例补充以下具体规则，**这些数字与选点方法不是论文公开的固定参数**：

- 一个虚拟模块占 `3×3` 个电极；模块之间留一整块模块宽度的通道。第一个模块左上角坐标为 `(3,3)`。
- 用输入液滴坐标的平均位置衡量距离；若距离相同，按从上到下、从左到右的顺序选模块。
- Mix 的两滴输入分别以模块中心左、右相邻电极为目标；Detect 的目标是模块中心。输出液滴的位置暂记在模块中心。
- 选址时就预留模块和输入液滴；只有操作真正启动时，该模块才出现在 `activeBlockages()` 中。
- 在 v0.2 中，液滴“已到达”和操作“已完成”由示例或测试手动报告；实际移动在 v0.3 接入。

v0.2 只能验证上层状态衔接和选址规则，不能作为论文路由效果的对照结果。

## v0.3 新增：按反馈逐步移动

v0.3 在 `RoutingTask` 对应的目标与 `UpperLayer` 之间接入 `Router`。整个演示的数据流是：

```text
就绪操作 → 上层选址 → RoutingTask → Router 规划下一步
                                  ↓
                         实际位置反馈、检查是否到达
                                  ↓
                      上层确认全部到达且操作区空闲 → 启动
                                  ↓
                      操作区域成为 blockage → Router 更新
```

| 代码 | 职责 |
| --- | --- |
| `routing_task.hpp` | 上下层共同认识的液滴编号、目标电极和操作编号。 |
| `router.hpp/.cpp` | 保存待运送任务；为每个目标用 BFS 生成代价场；每一步结合最新障碍和液滴位置选择动作；根据实际位置反馈判断到达。 |
| `upper_layer.hpp/.cpp` | 与 Router 共用同一份液滴位置；到达反馈必须与真实目标坐标一致，且模块内没有其他液滴才启动操作。 |
| `tests/router_tests.cpp` | 验证单滴移动、移动失败、动态障碍、多滴迎面相遇与代价场缓存。 |

### 路由规则与实时性

- 每个控制步只考虑上下左右四个相邻电极；没有安全动作时原地等待。Router **规划**动作后再接收**实际位置反馈**。若电极动作失败，位置保持原样，下一步依实际位置重新决策。
- 在当前障碍布局下，每个目标执行一次 BFS；同一目标可复用。操作障碍区改变时才清除旧场，下次使用时重建。普通控制步无需重算整张芯片的场。完成的目标若不再有任务使用，缓存会释放。
- 安全距离暂设为两滴液体的 Chebyshev 距离至少为 2，即水平、竖直和斜方向相邻都不允许。规划下一步时检查其他液滴的当前位置、上一时刻位置以及本步已规划位置。这是可配置的**工程假设**，不是论文公开的固定数值。
- 迎面相遇时用两步前瞻比较候选动作，并在平局时让不同编号的液滴偏向不同侧绕行；立刻退回上一个电极会增加 3 的选择代价。这两个确定性选择是为了复现可检查的绕行行为，**不是论文给出的固定参数**。
- v0.3 的 BFS 更新是按需同步执行；v0.8 对已缓存目标在环境变化后的重算加入后台线程。新目标的第一次代价场仍同步生成，保证当步有路线可用。当前示例只模拟电极位置和反馈，不生成真实驱动信号。

`Router` 的状态与操作完成仍分开：液滴真实到达会自动通知上层；Mix、Detect 的完成时刻和输出编号在示例中仍由程序报告。`cycle` 目前只是 dynamic DAG 的逻辑周期，不等于论文的物理执行周期。

## v0.3.1 新增：自己设置起点和终点

这一版增加了独立的 `dmf_custom_route.exe`。它只使用下层 Router，不运行 `Mix → Detect` 协议或上层选址。你可以在 `examples/route_case.txt` 中填写阵列尺寸和多滴液体的起终点；重新运行程序就会读取新内容，无需重新编译。默认文件如下：

```text
chip 5 5
separation 2
max_steps 50
trace 1
droplet 1 0 0 4 4
```

`chip` 后是阵列宽度、高度，所以这里是 `5×5`；坐标从 `(0,0)` 开始。`droplet` 一行依次写“编号、起点 x、起点 y、终点 x、终点 y”。增加更多 `droplet` 行即可测试多滴液体。`separation` 是可配置的安全距离；`max_steps` 是最多尝试的控制步数；`trace 1` 打印每一步，`trace 0` 只显示到达事件与最终结果，可减少大量控制台输出。以 `#` 开头的文字是注释。

输入会检查阵列大小、坐标范围、重复编号和起点安全距离。当前实验入口限制为最多 90000 个电极、400 滴液体、100000 个控制步，以免误填参数后长时间占用计算资源。若超过步数，程序会列出尚未到达的液滴、当前位置和目标位置；连续 10 步没有任何液滴移动时也会停止。**停止只说明当前路由策略未完成这次实验，不证明该布局在数学上无解。**

输入文件在程序启动时解析一次；正常控制步仍使用 v0.3 的 Router 与代价场缓存。打印大量轨迹会影响你观察到的总运行时间，因此需要评估计算性能时应将 `trace` 设为 `0`。目前没有把这项自定义实验的运行时间当作论文性能复现结果。

## v0.4 新增：操作计时与逐步协同

以前的双层演示需要手动报告 Mix、Detect 何时完成。现在 `ExecutionLoop` 把上层、Router 和操作完成反馈接到同一个**模拟控制步**中。`ModuleProfile` 增加 `duration_cycles`；演示用 Detect 的时长为 3 个运行控制步。这个数值是为了验证事件顺序而设的工程假设，论文中的具体操作时长应在复现实验参数确定后另行填写。

每一步按以下顺序执行：

```text
上一步的输出液滴和分支变为可用
    → 上层为就绪操作选址、预留液滴与模块
    → Router 接收任务；已在目标的液滴可立即触发操作启动
    → Router 读取当前运行模块的 blockage
    → Router 规划一步、收到模拟的实际位置反馈
    → 全部输入到达且模块空闲时，操作开始运行
    → 只给进入本步前已经运行的操作计时
    → 到时收到完成反馈、释放模块；输出下一步才可用
```

例如时长为 3 的操作若在第 1 步启动，第 2、3、4 步末分别消耗一个运行步，在第 4 步末完成。同一时间，其他液滴仍可继续路由。操作一开始，模块区域成为 blockage；完成时立即解除。`completeEarly` 可提前提交实际完成反馈并释放模块，输出仍从下一步开始可用。到达晚于预计时间的操作不会提前计时，模块也只有在真正启动后才成为运行障碍。

v0.4 的 `timed` 演示放置两项独立 Detect：近处液滴立即启动，另一滴在操作运行时继续前进。每步会显示移动、启动、完成及 blockage 数量；结束时显示代价场构建次数和 Router 决策的累计微秒数。计时只包住 `Router::planStep()`，不含控制台打印、上层选址、模拟反馈，也不代表硬件实时性保证。控制循环在单线程中按序模拟“路由与操作在同一时间段推进”，尚未实现后台计算线程或真实电极驱动。

`tests/execution_tests.cpp` 检验并行推进、操作时长、动态 blockage、输出下一步可用与提前完成；此前的测试仍保留。

## v0.5 新增：实际位置反馈与强制绕障

v0.4 的控制循环总假设液滴按命令成功移动。现在可向 `ExecutionLoop` 提供一个移动反馈函数：每收到一条移动命令，返回这一控制步观测到的液滴位置。反馈可为原位置（移动失败）或命令指定的下一位置（移动成功）；Router 会检查反馈是否合法，并以**实际位置**判断是否到达、下一步从哪里继续规划。`StepReport` 同时保留 `moves`（计划动作）和 `observed`（实际反馈）。不提供反馈函数时，沿用原先“移动总成功”的默认行为。

默认 `detour` 演示仍使用 **15×9** 阵列，两滴液体的起点改为 `(4,4)` 和 `(0,4)`；液滴 2 的目标是 `(10,4)`。横向直走会穿过 near 操作占用的 `x=3～5、y=3～5`，因此它必须先离开 `y=4`，绕过活动模块。示例把两项 Detect 的运行时长都设为 20 个控制步，并在第 2 步故意让液滴 2 的一次移动失败；这些数值和失败事件都是**用于验证的工程设置**，不是论文实验参数。

控制台的 `planned=(x,y)` 是 Router 希望到达的位置，`actual=(x,y)` 是反馈确认的位置。第 2 步会出现 `FAILED`，第 3 步重新从实际位置出发；液滴 2 随后沿上方绕行，并在 near 尚未完成时启动 far，此时 `blockages=2`。完成反馈和先前版本一样使模块释放。测试另外覆盖“最后一步移动失败时不能误报到达和启动操作”，并检查绕行期间不进入活动模块、最终完成两项操作。

此反馈入口用于模拟电极位置观测，尚未连接真实传感器。微秒计时仍仅统计 Router 规划动作，不含反馈函数和控制台输出。

## v0.6 新增：一条协议从输入跑到输出或废液口

之前动态 DAG 的分支演示和双层控制循环分别运行。这一版让同一条协议在一个控制循环里完成：

```text
输入液滴 1、2 → Mix → 新液滴 3 → Detect → 新液滴 4
                                           ├─ 检测结果为 output → 送到输出口
                                           └─ 检测结果为 waste  → 送到废液口
```

上层仍为 Mix、Detect 选择虚拟模块，等输入液滴到齐后启动并形成 blockage。对于 Output、Waste，上层读取预设的阵列边缘端口，生成普通 `RoutingTask`；Router 使用同一套逐步移动与到达反馈。端口不占用虚拟模块，也不形成操作区域障碍。到达端口后，终点操作在下一控制步完成并消耗该液滴。检测结果由仿真反馈提供，选中的流程块在检测完成后的下一步才加入动态 DAG；另一条分支不执行。

v0.6 示例使用 **15×9** 阵列，初始液滴分别位于 `(1,2)`、`(1,6)`，输出口为 `(14,4)`，废液口为 `(0,8)`。Mix 用时 3 个运行控制步，Detect 用时 2 个运行控制步，终点操作用时 1 个运行控制步。这些位置和时长是演示事件衔接的**工程假设**，并非论文实验参数。运行 `am_dmf protocol` 会连续展示 output 和 waste 两次独立仿真；每行显示本步新激活的分支、运送目标、液滴移动、操作启动与完成、活动 blockage 数量。示例结果分别在第 23 步和第 21 步结束，最终活动液滴数均为 0。具体完成步数依本工程的路由规则和演示参数而定，不是论文实验结果。

`tests/protocol_execution_tests.cpp` 检查两条分支、操作依赖和分支时序、端口到达后才能启动、终点消耗液滴、安全距离，以及无效或缺失端口。此前版本的演示和测试保留。

在 Visual Studio 里通过“文件 → 打开 → 文件夹”打开 `PROJECT/versions/v0.6`，在绿色运行按钮旁选择 **`am_dmf.exe`**，按 **Ctrl+F5** 即可看到两条分支的完整过程；无需打开“调试和启动设置”。在当前版本中，可使用 PowerShell 命令 `am_dmf.exe protocol` 运行相同演示。想只看一条分支，可运行 `am_dmf.exe protocol-output` 或 `am_dmf.exe protocol-waste`。选择 **`dmf_protocol_execution_tests.exe`** 并按 Ctrl+F5，会看到 `protocol execution tests: passed`。

## v0.7 新增：新操作区域启用前撤离无关液滴

上层为操作选定虚拟模块后，先把它标记为**即将占用的区域**，并把该区域和本操作的输入液滴编号通知 Router。Router 允许本操作的输入液滴进入，同时引导其他液滴避开该区域。如果无关液滴已经在里面，Router 用 BFS 搜索最近且可安全到达的区域外电极，临时将其作为撤离目标。液滴离开后，原来有运送任务的继续去原目标；原本没有任务的停在安全位置。只有输入液滴到齐、区域内没有无关液滴时，上层才启动操作并把区域变为正式 blockage。

```text
选址并预告区域 → 发现区域内的无关液滴 → 撤离到安全出口
            → 输入到齐且区域清空 → 启动操作 → 正式形成 blockage
```

默认 `evacuation` 演示使用 **9×9** 阵列：Detect 的输入液滴 1 起于 `(4,3)`，无关液滴 99 起于预留模块内的 `(4,5)`，模块范围是 `x=3～5、y=3～5`。第 1 步液滴 99 移动到 `(4,6)`；输入液滴继续前进，第 5 步才到位并启动 Detect，第 7 步完成。控制台会显示撤离目标、移动、清空区域、操作启动与完成，以及 blockage 数量。液滴 99 不属于该操作，检测完成后仍留在安全位置。

`tests/evacuation_tests.cpp` 检查静止液滴撤离、有原任务的液滴撤离后恢复、撤离移动失败后按实际位置重试、无安全出口时保持等待，以及区域正式启用前其他液滴不进入。`StepReport` 的 `evacuation_targets`、`evacuated` 和 `waiting_for_evacuation` 用于解释每一步发生了什么。

**当前工程规则：**即将占用的区域对无关液滴立即视为禁入，撤离出口按最短可行步数选取；相同步数按固定邻居顺序决定。论文提到按预计占用时间提前预告，并允许液滴在启用前视情况穿过区域。本版采用较保守的禁入规则，尚未建立精确的未来占用时间窗口。移动失败仍由 v0.5 的实际位置反馈处理；若没有安全出口，系统报告等待，不强行启用障碍。新障碍未经预告、直接困住液滴的处理仍待后续实现。这里的演示位置和时长是工程假设，不是论文实验数据。

## v0.8 新增：操作区域变化时异步更新代价场

代价场记录每个电极到目标的最短剩余步数。v0.7 在障碍变化后的首次路由决策中同步重算整张场；v0.8 把**已有目标的重算**交给一个后台工作线程。Router 先拍下障碍和预告区域的不可变快照，再发出更新任务。后台完成前，旧代价场只用于判断哪个方向更有希望；每个候选位置仍必须通过**当前**障碍、预告区域和液滴安全距离检查。新场准备好后，Router 在控制步边界切换。连续变化时只保留每个目标最新版本，旧计算结果不会覆盖新结果。

```text
障碍变化 → 保存当前布局快照 → 后台计算新版代价场
                 ↓                       ↓
      当前障碍继续做安全检查       完成后按版本号安装
                 ↓                       ↓
            旧场暂时指导方向 → 下一控制步使用新场
```

v0.8 独立快照的默认演示使用 **120×120** 阵列，液滴从 `(0,60)` 运送到 `(119,60)`。第 10 步在 `x=55～65、y=55～65` 加入障碍，第 40 步移除。当前版本使用 `am_dmf.exe async` 运行相同演示。控制台会显示变化通知、旧场使用、新场启用、最终到达、总步数和等待步数。后台计算结束的具体步数受系统线程调度影响；运行时可能与示例截图不同。`am_dmf.exe evacuation` 保留 v0.7 的撤离演示。

工程中的异步边界是**障碍变化后的重算**：首次遇到一个全新目标仍同步构建代价场；显式测试等待函数用于测试，不在正常控制循环中调用。若旧场把可行方向估成不可达，液滴可能暂等新场，故本版保证的是每步安全性，不声称所有可达任务必然完成。`cost fields built` 只计入已安装的场，不包括被丢弃的后台旧版本。

`dmf_async_cost_field_tests.exe` 检查连续变化只接受最新版、旧场期间不进入新障碍、多个液滴共用目标，以及后台计算完成后的切换。`dmf_field_benchmark.exe` 对同一场景重复 10 次，分别统计“变化通知”和“变化后首次决策”的耗时中位数、总步数与等待步数；比较 v0.7 时需分别编译两个版本的 Release 程序。这个小场景只能检验局部开销与功能，不能替代论文的大规模实验或实时性上界证明。

## v0.9 新增：启用操作区域前检查是否会切断运送路线

v0.7 已能把**位于预告操作区域内**的无关液滴撤走。v0.9 处理另一种情况：液滴仍在区域外，但该区域一旦变为正式 blockage，液滴与自己的目标可能被隔在两边。Router 会在操作启动前，分别检查“当前障碍布局”和“再加入该操作区域后的布局”。如果当前能到达、加入后不能到达，就标记这滴液体需要**提前转移**；上层暂缓启动操作。

```text
选定操作区域 → 假设它已启用，检查路线是否连通
                               ↓
                    会断路：暂缓操作启动
                               ↓
          液滴先穿过尚未启用的区域，到达目标一侧
                               ↓
                    再允许操作启动
```

连通性结果按操作区域缓存，多滴液体共用；同一布局的普通控制步不重复生成整张连通图。提前转移时，Router 用 BFS 寻找一条到“目标所在一侧”的短路径，每一步仍检查实际障碍、其他液滴的当前位置与上一位置、安全距离。位置反馈失败时，从实际位置重试；路径被其他液滴挡住时重新搜索。如果当前没有安全转移路径，`waiting_for_crossing` 会报告等待，操作继续保持预留状态。提前转移期间，所有预留操作区域暂停启用，以免液滴正穿过时区域突然变成障碍；这是一条偏保守的工程规则，可能减少并行操作数量。

v0.9 独立快照的默认演示使用 **9×9** 阵列。上下两块固定障碍分别占 `x=3～5、y=0～2` 和 `x=3～5、y=6～8`，中间留下唯一通道 `x=3～5、y=3～5`；Detect 预留的区域恰好覆盖通道。液滴 2 从 `(1,4)` 送往右侧输出口 `(8,4)`，先穿过通道到达右侧，Detect 才启动。当前版本使用 `am_dmf.exe crossing` 运行相同演示。示例中，前 6 步执行提前转移，第 10 步启动 Detect，第 12 步完成；具体步数由本工程的移动和操作时长设定决定，不是论文数据。固定障碍是仿真场景的一部分，不表示芯片硬件接入。

`dmf_crossing_tests.exe` 检查安全提前转移、通道被另一滴液体占用时保持等待、移动失败后按实际位置重试。`StepReport` 的 `crossing_modules`、`waiting_for_crossing` 和 `held_modules` 说明本步哪些液滴正在转移、哪些仍在等待、哪些操作区域暂缓启动。`connectivity_check_microseconds` 记录上层在控制步中请求断路检查的时间；Router 自身规划时的再次检查计入 `routing_microseconds`。

本版只为**已有运送目标**的液滴提前检查连通性。若没有安全转移路线，系统会等待并报告原因，尚不会自动更换操作区域；若正式障碍未经预告就覆盖液滴所在电极，仍视为无效仿真状态。多个预告区域之间更复杂的调度和完成性保证也有待后续实验验证。

## v1.0 新增：从产生液滴到分支输出的完整仿真链

本版让此前只有逻辑表示、没有上层执行规则的 **Dispense** 和 **Split** 进入同一控制循环。Dispense 是从芯片边缘入口产生一滴液体；Split 是把到位的一滴分成两滴。dynamic DAG 原本已能记录零输入及多个输出，本版补上端口、操作位置、输出位置和安全检查。

| 操作 | 输入与输出 | 当前仿真规则 |
| --- | --- | --- |
| Dispense | 零滴输入 → 一滴输出 | 根据操作名称选择边缘入口；入口及其安全距离内有液滴时等待。运行期间入口是 `1×1` blockage，完成后新液滴出现在入口。 |
| Split | 一滴输入 → 两滴输出 | 输入到达虚拟模块中心后开始；分裂用时由 `ModuleProfile` 配置。完成后两滴分别位于中心左、右相邻电极，间距为 2。 |

Split 的操作形状按论文提到的 `3×1` 例子配置，但当前 Placer 仍以 `3×3` 虚拟模块预约和选址，运行期间也把整个模块作为保守的 blockage。操作用时、入口坐标、两滴产物的具体位置，以及此处的区域占用方式都是**工程假设**；本工程没有复现芯片的电极驱动序列。

操作输出之前会检查新液滴之间、以及它们和其他液滴之间是否满足配置的安全距离。若入口或 Split 出口暂时没有安全空间，本步报告 `waiting_for_output_space`，操作继续等待。完成反馈只取一次并保存，下一步继续尝试释放同一批输出，避免重复申请液滴编号。Router 与上层的安全距离配置不一致时，控制循环会拒绝启动。已到输出口或废液口的液滴仍按 v0.6 的规则被消耗。

v1.0 独立快照中的默认 `am_dmf.exe` 在 **15×9** 阵列分别运行 `output` 与 `waste` 两种检测结果；当前版本使用 `am_dmf.exe full` 运行同一演示：

```text
source_a、source_b 两次 Dispense → Mix → Split
                                      ├─ 产物 4 → Detect → 按结果 Output 或 Waste
                                      └─ 产物 5 → Waste
```

示例中两个入口为 `(0,1)`、`(0,7)`，输出口为 `(14,4)`，废液口为 `(0,8)`；Dispense、Mix、Split、Detect 分别用 1、3、2、2 个运行控制步。`output` 分支在第 34 步完成，`waste` 分支在第 32 步完成，两次仿真最终均没有活动液滴。这些步数属于本工程的示例结果，不是论文实验数据。控制台还分别统计路由、连通性检查和障碍更新的微秒数，均不包含大量控制台打印时间。

`dmf_full_protocol_tests.exe` 检查两种动态分支、两滴 Split 产物的位置和后续消费、入口被占用时的等待、同一入口不能同时用于两次 Dispense、输出安全空间不足时的等待与反馈复用、液滴编号不覆盖已有液滴，以及无效 Dispense/Split 输入输出数量。原有 v0.1～v0.9 的测试和演示保留。

## v1.1 新增：两组检测分别决定后续操作

论文的 Parallel Mixing with Branching 实验同时执行多组混合，每组检测后的液滴分别走 Output 或 Waste。v1.0 的 `BlockSpec` 只能保存一个 `DecisionSpec`，所以只能表达一组检测分支。v1.1 将其改为 `decisions` 列表：每个 Detect 有自己的结果和下一流程块，检测 A 完成后会把 A 的后续操作放入下一控制步；即使检测 B 仍在运行，也无需等待。dynamic DAG 原有的多条待激活分支队列接收这些结果。

```text
第 A 组：Dispense ×2 → Mix A → Detect A → Output / Waste
第 B 组：Dispense ×2 → Mix B → Detect B → Output / Waste
                              ↑ 两组分别按自己的检测结果分流
```

演示使用 `VirtualChip(4,2)`，对应 **27×15** 阵列和 8 个可选虚拟模块；A 组入口 `(0,1)`、`(0,7)`，B 组入口 `(26,7)`、`(26,13)`，Output 口 `(26,0)`，Waste 口 `(0,14)`。这些位置、操作时长和反馈结果均是工程假设。两个检测决定可以激活同名的 Output 或 Waste 流程块，但每次激活都是独立实例，不会混用液滴。共享终点时液滴需要遵守安全距离。

| A 组结果 | B 组结果 | 本工程示例完成步数 |
| --- | --- | ---: |
| Output | Output | 77 |
| Output | Waste | 89 |
| Waste | Output | 65 |
| Waste | Waste | 77 |

默认运行 `am_dmf.exe` 会依次打印四种结果的摘要；`am_dmf.exe parallel-ow` 等模式会打印每一步的移动、操作开始/完成、分支激活。`parallel-oo`、`parallel-wo`、`parallel-ww` 分别对应另外三种结果。在 Output/Waste 示例中，A 组 Detect 于第 16 步完成，第 17 步激活自己的 Output 流程；B 组的 Mix 到第 56 步才启动。这说明 A 的分支没有被 B 的进度挡住。`dmf_parallel_branch_tests.exe` 检查四种结果、液滴安全距离、两个检测同一步完成、分支相互独立，以及错误决策配置被拒绝。

摘要里的 `loop time avg/max` 是单个控制步执行 `ExecutionLoop::step()` 的平均/最长墙钟时间，包含本示例的反馈函数，不含控制台输出；数值随机器与系统调度变化。它不能直接对比论文的 Python 决策时间。当前虚拟阵列规则也不能直接生成论文 Table I 的 30×30、60×60 布局，协议规模和输入生成规则尚未对齐；上表只是本工程可重复的小规模功能实验。Router 在其他布局中仍可能出现长时间绕行，不能由本例推出普遍的完成保证。

## v1.2 新增：逐次实验记录与安全核对

v1.2 复用 v1.1 的两组并行协议，不改变选址和 Router 的决策规则。该版本的 `dmf_parallel_experiments.exe` 对四种检测结果各运行 5 次，生成 20 行逐次结果和 4 行汇总；v1.3 的同名程序扩展为两种执行模式的对照，详见下节。每一次都从空白仿真重新开始；若超出 250 步或执行报错，该次会保留为 `timeout` 或 `failed`，不会进入成功运行的步数均值。

| 固定参数 | 本工程试验设置 |
| --- | --- |
| 阵列、虚拟模块 | `VirtualChip(4,2)`，27×15、8 个可选模块 |
| 安全距离 | Chebyshev 距离至少 2 |
| 入口 | A 组 `(0,1)`、`(0,7)`；B 组 `(26,7)`、`(26,13)` |
| 端口 | Output `(26,0)`；Waste `(0,14)` |
| 操作时长 | Dispense 1 步、Mix 3 步、Detect 2 步；终点操作 1 步 |
| 分支 | Output/Output、Output/Waste、Waste/Output、Waste/Waste |
| 随机种子 | `none`：这四个案例没有随机输入；异步线程调度仍可能影响耗时 |

每一步结束后，记录器检查液滴没有越界、液滴之间满足安全距离，并要求控制步编号连续。`route_requests` 是本步新下发的路由任务数；`route_arrivals` 取自 Router 确认的到达事件，不把任务下发误当成完成。`throughput = route_arrivals / steps`，只描述这个有限协议案例；它**不能替代**论文连续产生路由任务的吞吐量实验。正常结束还会核对所有请求均有到达事件、没有剩余液滴、三个流程块全部完成。

CSV 中 `plan_step_*_us` 只计 `Router::planStep()` 的计算时间；`loop_*_us` 计整个 `ExecutionLoop::step()`，包含上层、障碍更新、连通性检查及仿真反馈，不包含控制台输出和实验记录器检查。两种计时口径都不是论文 Python 实现的 DecT 数值。CSV 中失败运行的数值格留空，汇总保留失败次数；若某分支全部失败，其均值也留空。

可在 PowerShell 中从工程目录运行：

```powershell
.\build\Debug\dmf_parallel_experiments.exe experiment_trials.csv experiment_summary.csv
```

在 Visual Studio 打开相应版本文件夹后，选择启动项 `dmf_parallel_experiments.exe` 并按 Ctrl+F5；控制台会显示两个 CSV 文件名。文件保存位置是 Visual Studio 为该启动项设置的**工作目录**，可通过给可执行文件传入两个完整路径来指定位置。v1.2 只建立可靠的记录口径和小规模检查；论文的 30×30、60×60 协议生成和 Router 大规模任务流仍待后续版本。

## v1.3 新增：动态分支与批次等待对照

论文的框架层对照方法在一批并行操作结束后，才统一处理检测结果产生的后续任务。v1.3 在**同一条两组混合协议**上增加 `after_batch` 模式：第一组 Detect 完成后，其分支先排队；第二组及其他当前操作全部完成后的下一控制步，两条分支才一起激活。原有 `immediate` 模式仍在检测完成后的下一步激活该组分支。两种模式使用同一 Router、模块布局、入口、端口、操作时长和检测结果，只改变分支何时放行。

`DynamicDag::advanceCycle()` 每步仍让新液滴可用；批次屏障只保留待激活分支。测试检查了两个检测结果不会丢失，以及普通操作所需的新液滴不会被屏障误延迟。`dmf_parallel_experiments.exe` 现在为四种分支组合、两种模式分别运行 5 次，生成 40 行逐次记录和 8 行汇总；CSV 中的 `mode` 区分模式，失败和超时仍单独计数。

| A / B 检测结果 | immediate 步数 | after_batch 步数 |
| --- | ---: | ---: |
| Output / Output | 77 | 89 |
| Output / Waste | 89 | 89 |
| Waste / Output | 65 | 77 |
| Waste / Waste | 77 | 89 |

这些是当前 **27×15、两组混合**演示的结果，不能当作论文 Table I 的复现数据。`after_batch` 只实现了批次等待这项可独立验证的规则；论文对照方法的完整实验生成与整体合成实现未公开。本实验没有使用论文的 30×30、60×60 阵列、9/15/25 组混合及 100%/90%/70%/50% 输出设置。不同路径可能出现步数相同，因此不预设动态模式在每个案例都更快。

运行 `am_dmf.exe` 可看原动态模式的四行摘要，运行 `am_dmf.exe batch` 可看批次模式的四行摘要；`parallel-ow`、`batch-ow` 分别逐步打印同一 Output/Waste 案例。Visual Studio 中直接选择 `dmf_parallel_experiments.exe` 并按 Ctrl+F5，可生成并排比较两种模式的 CSV。

## v1.4 新增：论文第一类协议的最小规模试验

`VirtualChip` 新增“模块网格 + 实际电极宽高”的构造方式。`VirtualChip(4,4,3,30,30)` 中，前两个 `4` 表示横向 4 列、纵向 4 行，共 **16 个可供选址的模块**；`3` 表示每个模块占 3×3 个电极；最后两个 `30` 才是芯片的实际宽和高。模块没有铺满芯片：以横向为例，左边留 3 列，4 个模块共占 12 列，模块之间的 3 段通道共占 9 列，右边还留 6 列，合计 `3+12+9+6=30`。模块横向范围依次是 `x=3～5、9～11、15～17、21～23`，纵向同理。模块是可选的操作位置，**不是** 9 组任务各自固定占有的 9 个区域。旧构造方式和旧案例的尺寸保持不变。

新实验建立 **9 组** `Dispense ×2 → Mix → Detect → Output/Waste`；每组先从两个独立入口各产生一滴液体，所以需要 `9×2=18` 个入口电极。完成时核对 9 个终点流程块、45 个操作实例、36 个已下发且已到达的路由任务，以及没有剩余液滴。

| 参数 | v1.4 的设置与出处 |
| --- | --- |
| 阵列和组数 | 30×30、9 组混合：对应论文 Table I 的最小配置 |
| 模块 | 横向 4 列、纵向 4 行，共 16 个 3×3 虚拟模块；模块间距与边缘留白是工程假设 |
| 18 个入口 | 9 组任务各有 2 个入口；左边 3 对、右边 3 对、上边 2 对、下边 1 对，共 `（3+3+2+1）×2=18` 个电极：工程假设，坐标见 `sourcePorts()` |
| Output / Waste 口 | `(29,0)` / `(0,29)`：工程假设；当前各只有一个端口 |
| Dispense / Mix / Detect 时长 | 1 / 3 / 2 控制步：沿用演示值，并非论文公开的实验时长 |
| 分支概率 | 100%、90%、70%、50%：每组 Detect 分别按该概率选择 Output，否则选 Waste；这是仿真的随机输入，不是液滴移动成功率 |

例如在 90% 场景中，**每一组**都有 90% 的机会走 Output、10% 的机会走 Waste；9 组各抽取一次，单次实验可能出现 9 组 Output，也可能是 8 组 Output、1 组 Waste 等，并不要求恰好有 90% 的组走 Output。CSV 的 `outcome_pattern` 用 9 个 `O`/`W` 记录本次真正抽出的结果；`seed` 用于重现这 9 次抽取。两种调度模式共用同一串结果，以便比较。

`dmf_paper_parallel_experiments.exe` **默认只运行 100% 输出场景**：五个种子、两种模式，共 10 次；成功后生成 `paper_parallel_scenario1.csv`，退出码为 0。传入 `--all` 才运行四类场景共 40 次，生成 `paper_parallel_trials.csv`。CSV 同时保存 `seed`、九个结果组成的 `outcome_pattern`（`O` 为 Output、`W` 为 Waste）、实际输出数、模式、完成状态、步数和耗时。两种模式使用完全相同的种子和结果串。单次九组任务中的 90% 等数值是**生成概率**，不意味着结果数量恰好等于百分比。

当前路由策略在部分分支组合中可能长时间绕行。程序达到 1000 步后将该次标为 `timeout`，附带液滴位置、目标和未完成操作；完整实验只要出现超时或错误就返回非零退出码。**失败行保留在 CSV 中，不能据仅成功的行比较两种模式的性能。**在已运行的一轮 Debug 检查中，全部输出的 10 次均完成，四类场景的 40 次中有 4 次超时；两轮 Release 完整实验分别有 3 次和 4 次超时。相同种子只固定检测结果，异步代价场的完成时刻仍可能改变路由路径和执行步数；即使全部输出案例均完成，不同运行的步数也可能不同。因此本版既没有普遍完成保证，也不能作为论文 Table I 的数值复现。

在 Visual Studio 中打开 `PROJECT/versions/v1.4`，选择 `dmf_paper_parallel_experiments.exe` 并按 Ctrl+F5，可先看到全部输出场景的结果文件；想运行全部场景，在终端执行 `dmf_paper_parallel_experiments.exe --all`。输出 CSV 位于运行时的工作目录；也可在命令末尾给出完整的文件路径。测试入口 `dmf_placement_tests.exe` 检查精确阵列边界，CTest 的 `paper_parallel_scenario1` 检查 10 次完整仿真。

在 Visual Studio 打开 `PROJECT/versions/v1.5` 并生成 `dmf_paper_parallel_experiments.exe`。调试启动参数填写 `--diagnose`，或者在生成目录的终端执行：


### 这次查到了什么

Release 下六次诊断的 `fresh` 轨迹一致，均未使用旧代价场。从第 105 步起，液滴 2 停在 `(5,4)`，液滴 1 在 `(7,5) → (8,5) → (8,4) → (7,4) → (7,5)` 循环，第一组 Mix 因输入未到齐保持预留。以第 1000 步为例，向 `(6,5)` 移动会进入液滴 2 的安全范围。另两个候选 `(8,5)`、`(7,6)` 的评分和两步前瞻相同，固定的候选顺序使 Router 选了 `(8,5)`，重新进入循环。日志中 `near_current` 表示离另一滴的当前位置太近，`score` 包含折返惩罚，`next` 是前瞻一步的代价，`field` 与 `layout` 相等表示这一决策使用最新代价场。

冻结第 999 步结束时的布局，可以逐格核对这条可走的路线：

```text
(7,5) → (7,6) → (6,6) → (5,6) → (4,6) → (3,6) → (3,5) → (3,4)
```

它每步只移动一格，每个落点与液滴 2 的 Chebyshev 距离均为 2。当时没有运行中的障碍，唯一的预留区域属于该 Mix，允许液滴 1 进入。就这一案例而言，当前 Router 的评分和平局顺序会造成循环，即使代价场已经更新。日志记录本身也会影响后台线程获得运行时间的时机，因此诊断运行的超时次数不能用来估计常规实验的超时率。后续可以用这段具体轨迹检验路由修正。

## v1.6 修正 Router 的候选选择和短循环

Router 先比较下一格的代价，同分时比较再往前一步能达到的最低代价。前瞻也检查当前障碍、液滴间距和预留区域。v1.5 的折返额外加 3 已取消。两项代价都相同时，仍优先避免立刻折返，其余平局按原有固定顺序处理。

只调整评分就能解决 `1601`，但回归测试发现迎面相遇案例会反复移动。v1.6 因此添加了一条工程规则。普通路由重复同样的 2～4 步位置序列两遍时，针对该液滴做一次 BFS，把其他液滴和障碍按当前状态固定下来寻找绕行路径。原地等待会打断循环检测。找到路径后，每步仍按当前安全规则检查下一格。布局改变或下一格已不可走时，丢弃缓存路径。移动失败时保留尚未走成的一步。

小规模并行测试还复现了共享代价场的另一种等待。操作已经释放模块，旧场却仍把液滴周围的格子标成不可达。若有合法相邻格且旧场把它们全部标为不可达，Router 只为该目标获取或同步计算当前代价场。其他正常决策继续使用异步更新。上述两条处理是本工程对论文路由方法的补充。

### 验证结果

- `1601` 的固定输入在 v1.5 的最新代价场模式中重现超时。v1.6 的异步和最新代价场诊断均在 **58 步**完成。自动回归还核对了所有 **36 个路由任务**到达。
- 同一台电脑交替运行两版 Release，沿用 40 条固定输入，重复 5 轮。v1.5 有 **181/200** 次完成、19 次超时，v1.6 有 **200/200** 次完成。
- 在两版都完成的 181 对试验中，平均控制步从 **113.50** 降至 **62.90**，平均每次试验的 Router 决策累计耗时从 **750.36 μs** 降至 **624.34 μs**。用累计决定耗时除以总控制步，约从 **6.61 μs/步** 升至 **9.93 μs/步**，其中包括没有调用 Router 决策的控制步。这些数字只描述这批仿真，仍受机器和线程调度影响。

## v1.8 整批规划对照

第一类协议中，所有 Detect 完成后才有完整的 Output/Waste 任务名单。`static_batch` 在这时读入整批任务和当前液滴位置，复制一份状态，用同一个 Router 在副本里规划整个批次。规划时模拟出口占用，液滴到端口之后再留一个控制步，随后由 Output 或 Waste 消耗。只有计划完整时才开始实际移动。回放仍逐步校验实际位置、障碍和安全距离，并用现有控制循环完成 DAG 操作。

| 模式 | 分支何时放行 | 何时计算终点路线 |
| --- | --- | --- |
| `immediate` | 对应的 Detect 完成后的下一步 | 边移动边计算 |
| `after_batch` | 所有当前操作完成后的下一步 | 边移动边计算 |
| `static_batch` | 所有当前操作完成后的下一步 | 复制状态，规划完整批次后回放 |

这里的整批规划只覆盖第一类协议最后的终点阶段，前段的 Dispense、Mix、Detect 沿用原有控制循环。它依赖仿真中的理想移动反馈，规划策略是本工程根据论文流程作的实现。规划占用真实计算时间。因为在移动前完成，它不增加模拟控制步。预规划上限为 1000 个路由步，若超出则把本次记为失败，并在 CSV 保留原因。

## 当前边界与后续步骤

v0.6 已将 Mix、Detect、Output、Waste 贯穿到同一次仿真；v0.7 新增对**提前预告的操作区域**进行安全撤离；v0.8 对已有目标在障碍变化后的代价场重算使用单个后台线程；v0.9 能在区域启用前识别并处理目标被隔断的液滴；v1.0 让 Dispense、Split 也加入同一次协议仿真；v1.1 支持同一流程块的多个独立检测决定；v1.2 给四种小案例增加逐次统计和安全核对；v1.3 增加批次等待对照；v1.4 建立 30×30、9 组混合的试验入口并暴露部分场景的路由超时。入口、操作时长、分裂产物位置及部分路由与撤离规则是工程假设。**还没有**自动更换不可行操作区域、未预告障碍困住液滴时的完整处理，也没有论文实验所用的完整大规模基准和可靠对照结果。当前实现不生成真实电极驱动序列。

论文没有精确规定所有周期内事件的先后边界。当前固定为“本步完成的操作，其输出液滴和检测分支从下一步开始可用”；这是工程假设。`ExecutionLoop` 默认使用理想移动反馈，v0.5 允许注入失败或成功的位置反馈，但尚未接硬件反馈入口。

下一步计划对齐论文测试协议、阵列尺寸和实验参数，建立对照算法及大规模案例，再决定未预告障碍与无法释放输出时的进一步调度规则；PIBT 改进在原论文版本稳定后单独开展。每个完成版本都同时保存 GitHub 标签和 `PROJECT/versions/版本号` 的源码副本。
